# 실행 방법론

결론: 아래 방법은 각각 "언제 / 절차 / 종료 조건 / 흔한 함정" 순서로 쓴다.
상황에 맞는 것 하나를 골라 그 절만 읽는다. 배경 원칙은 philosophy.md에 있다.

## 1. 블라인드 다관점 리뷰 루프
**언제**
- 코드나 문서를 내보내기 직전, 내 프레임 밖의 눈이 필요할 때.
**절차**
1. 맥락을 모르는 병렬 하위 에이전트를 관점별로 하나씩 띄운다. 서로 결과를 보지 않는다.
2. 관점과 접지를 다르게 준다.
   - 동작: 변경이 의도를 달성하는지. 관련 테스트를 직접 실행한다.
   - 실패 경로: 경계값, 예외 전파, 호출자 가정, 보안, 비용.
   - 정합: 이웃 코드와 레포 규약에 맞는지.
   - 필요성: 추가한 코드마다 호출자를 찾는다. 못 찾으면 P1이다.
3. 대상은 경로나 변경 범위 지정(브랜치 비교 명령)만 준다. diff를 붙여넣지 않는다.
4. 프롬프트는 글자 그대로 고정한다. 라운드마다 바꾸지 않아야 추이가 의미를 갖는다.
5. 결과는 구조화 출력(P1, P2, 위치, 근거)으로 받는다. 보고 원문이 내 컨텍스트를 먹지 않게 한다.
6. 지적을 그대로 받지 않는다. 각 지적을 코드·테스트 실행·이웃 코드로 내가 다시 확인한다.
   - 틀린 지적은 틀렸다고 적고 고치지 않는다.
7. 채택한 것만 고친다. 고친 뒤 같은 프롬프트로 다시 돌린다.
**종료 조건**
- 신규 P1이 0이다.
- 타당하고 금방 고칠 수 있는 P2를 다 고쳤다.
- 남은 P2는 사유와 함께 기각하고 보고한다.
- 신규 여부는 내가 판정한다. 리뷰어에게 이전 지적을 주지 않는다.
**흔한 함정**
- 리뷰어에게 줄 것: 변경 요약, 의도 설명, 이전 지적, "잘 썼는지 봐 달라"는 사전 판단. 모두 주지 않는다.
- 실행 환경 설명에 "어떤 테스트를 돌릴지"를 적으면 리뷰어가 그 범위에만 머문다.
  - 적을 것은 테스트를 "어떻게" 돌리는지뿐이다. 무엇을 돌릴지는 리뷰어가 호출부에서 찾는다.
- 완결성만 묻는 리뷰는 "더 넣어라"로만 밀린다. 필요성 관점을 따로 둔다.
- "신규 0 두 번"을 고집하면 가장자리 P2가 끝없이 나온다. 위 종료 조건을 쓴다.
- 문서 리뷰는 관점을 사람 역할로 나눈다 (작성자 본인, 데이터 검증자, 전문가, 회의론자, 무맥락 독자).
  - 최소 하나는 문서를 믿지 않고 원본을 직접 재계산한다.
  - 점수 같은 숫자 항목을 넣어 라운드 간 추이를 남긴다.

## 2. 재현은 실패 테스트 먼저
**언제**
- 버그 보고나 리뷰 지적에 재현 조건이 붙어 있을 때.
**절차**
1. 재현 조건을 회귀 테스트로 옮긴다.
2. 고치기 전에 그 테스트가 **실패하는 것**을 확인한다.
3. 코드를 고쳐 통과시킨다.
4. 수정을 되돌려 테스트가 다시 실패하는지 확인한다 (방법 3과 연결).
5. 고친 뒤 재현 경계가 옮겨 가면 경계 주변을 훑는 테스트로 바꾼다.
   - 단일 입력 대신 불변식(예: 결과가 항상 상한 이하)을 고정한다.
**종료 조건**
- 실패 → 통과 → (되돌리면) 실패의 세 상태를 모두 직접 본다.
**흔한 함정**
- 추정으로 먼저 고치면 같은 지적이 다시 돌아와 루프가 길어진다.
- 처음부터 통과하는 테스트는 아무것도 증명하지 못한다.
- 인과가 걸린 수정은 먼저 돌려 보고 고친다. 확인하지 않은 인과를 코드나 문장에 쓰지 않는다.

## 3. 뮤테이션 검증
**언제**
- 테스트가 정말 그 동작을 고정하는지 의심스러울 때.
**절차**
1. 검증할 불변식마다 소스를 일부러 깨뜨린다 (조건 반전, 분기 삭제, 상수 변경).
2. 테스트가 실패하는지 본다. 통과하면 그 테스트는 불변식을 고정하지 못한다.
3. 원본은 파일이 아니라 **메모리 변수**로 들고, `try/finally`에서 되써서 복원한다.
4. 끝나면 변경 상태를 보여 주는 명령(`git diff --stat`)으로 의도 밖 파일이 없는지 본다.
**종료 조건**
- 모든 뮤테이션이 테스트에 잡혔다.
- 소스가 원래 상태이고, 변경 목록에 의도한 파일만 있다.
**흔한 함정**
- 임시 디렉토리에 백업을 두면 다른 작업이 지울 수 있다. 복원이 안 되고 뮤테이션이 소스에 남는다.
- 메모리 압박 중 돌린 스윕이 죽으면 뮤테이션 상태로 남는다. 죽었으면 즉시 변경 상태를 확인한다.
- 디렉토리 단위로 포매터를 돌리면 무관한 파일(문서 코드 블록 등)까지 바뀐다.
  - 바꾼 파일만 지정하고, 포매터 버전은 레포가 고정한 것을 쓴다.

## 4. before/after 검증과 원복
**언제**
- 고친 것이 실제로 증상을 없애는지 증명해야 할 때.
**절차**
1. 증상을 한 문장으로 적고, "무엇이 보이면 재현 성공인가"를 먼저 정한다 (화면 값, 로그 한 줄, DB 행).
2. 현재 환경의 값을 직접 읽는다. 문서나 옛 스크립트에 박힌 ID·키를 믿지 않는다.
3. 양쪽(before, after)을 **같은 방식**으로 만든다.
   - 배포본을 "before"로 쓰면 내 변경이 아니라 그 사이의 다른 변경을 재게 된다.
   - 같은 소스 트리에서 경로만 바꿔 양쪽을 만든다.
4. 측정은 숫자로 남긴다 (오프셋, 행 수, 화면 값). "된다/안 된다"로 쓰지 않는다.
5. 왕복 2사이클: 적용 → 확인 → 원복 → 확인 → 재적용.
6. 내가 켠 것만 되돌린다. 남의 리소스는 두고 보고에 적는다.
**종료 조건**
- 원복 후 상태가 처음과 같다.
- before와 after의 숫자 차이가 증상과 일치한다.
- 재현이 안 됐다면 안 됐다는 사실과 시도한 조건을 남긴다 (무엇이 다른지가 정보다).
**흔한 함정**
- 소스를 바꿔도 실행 중인 프로세스는 옛 코드를 들고 있을 수 있다. 재시작하고 새 프로세스를 다시 잡는다.
- 교체가 조용히 실패해도 서비스는 뜬다. 바뀐 파일·심볼이 실제로 보이는지 확인한다.
- 설정 병합은 목록을 합치지 않고 통째로 교체하는 도구가 많다. 기본값을 옮겨 적고 더한다.

## 5. 경로 전수 나열 후 결론
**언제**
- "X가 되나 안 되나", "어디서 쓰이나" 같은 질문을 받았을 때.
**절차**
1. 경로 하나를 찾은 순간 결론 내지 않는다.
2. 먼저 **입구 × 종류 × 저장·전달 방식**을 표로 전수 나열한다.
   - 입구: 화면 컴포넌트, API(여러 형식), 배치.
   - 종류: 같은 기능을 쓰는 서로 다른 객체 유형.
3. 검색은 "대표 하나 찾기"가 아니라 "전부 찾기"로 한다.
   - 같은 역할의 심볼을 전수 grep하고, 갈래의 수부터 센다.
4. 질문에 해당하는 칸을 짚고, 결론에 "어느 갈래 기준인지"를 붙인다.
**종료 조건**
- 표의 모든 칸이 확인됨 / 해당 없음 / 미확인으로 채워졌다.
**흔한 함정**
- 템플릿이나 예시 하나만 보고 실제 데이터를 무시한다.

## 6. 근본 원인 단위로 문서 쪼개기
**언제**
- 증상이 많은 조사를 문서로 정리할 때.
**절차**
1. 쓰기 전에 인과 트리를 그린다.
2. 원인 하나에 문서 하나를 만든다. 증상은 그 문서의 하위 절이다.
3. 문서 구조는 "원인 → 파장(영향받는 축별) → 방향"으로 한다.
4. 제목과 요약은 질문이나 명제로 쓴다.
   - 독자가 궁금한 것은 사례가 아니라 일반화 가능한 교훈이다.
   - 시간 순서 서사는 본문의 증거로 내린다.
5. 문서마다 독립 완결로 만든다 (근거 쿼리 포함). 종합 문서는 진입점과 링크 허브로 최소화한다.
**종료 조건**
- 문서 하나가 원인 하나만 다루고, 다른 문서를 읽지 않고도 성립한다.
**흔한 함정**
- 주제별로 쪼개면 문서 수만 늘고 인과가 흩어진다.

## 7. 정정 이력 남기기
**언제**
- 이전 결론이 틀렸다고 밝혀졌을 때.
**절차**
1. 옛 문장을 지우지 않고 "정정" 항목을 추가한다.
2. 항목에 쓸 것: 날짜, 옛 주장, 새 사실, 뒤집은 근거(1차 출처).
3. 옛 주장을 인용한 다른 문서가 있으면 같이 고친다 (전수 검색).
**종료 조건**
- 읽는 사람이 현재 결론과 과거 결론의 차이를 한 번에 알 수 있다.
**흔한 함정**
- 조용히 덮어쓰면 같은 오류가 재발한다.

## 8. 범위 넓히기 전 항목·장부 확인
**언제**
- 리뷰 지적이 "같은 부류의 다른 지점"으로 계속 번질 때.
**절차**
1. 넓히기 전에 확인한다.
   - 요청 항목 목록과, 변경 하나가 항목 하나에 대응하는지.
   - 같은 부류의 인벤토리(알려진 문제 목록)가 이미 있는지.
2. 리뷰 시작 전에 닫을 범위(장부의 몇 줄)를 정한다.
3. 범위 밖 지적은 장부 후보로 넘긴다.
4. 범위를 넓히는 채택은 요청자에게 한 줄로 묻는다.
**종료 조건**
- 변경이 정한 범위 안에서 닫히고, 범위 밖 항목이 장부에 기록됐다.
**흔한 함정**
- 인벤토리가 이미 있는데 라운드가 끝난 뒤에야 읽는다.
- 범위 결정은 요청자의 몫이다. 내가 조용히 넓히지 않는다.

## 9. 완료의 정의: 실제 실행 검증
**언제**
- "다 됐다"고 보고하기 직전.
**절차**
1. 완료 조건을 시작할 때 적어 둔다.
2. 사용자 경로를 끝까지 직접 실행한다 (입력 → 처리 → 출력). 코드를 읽은 것으로 대신하지 않는다.
3. 실행한 명령과 관측한 결과를 보고에 쓴다.
4. 실행하지 못한 부분은 실행하지 못했다고 명시한다.
5. 제출 직전 점검표:
   - 관련 테스트와 전체 테스트가 통과한다.
   - 변경 목록에 의도한 파일만 있다.
   - 새 코드마다 호출자를 댈 수 있다.
   - 설명 문서의 문장이 변경과 일치한다.
**종료 조건**
- 관측한 결과가 완료 조건과 일치한다.
- 병합·제출과 실제 동작 확인은 다른 단계다. 동작 확인까지 끝나야 완료다.
**흔한 함정**
- 단위 테스트 통과를 완료로 보고한다.
- 합쳐졌다는 사실을 동작한다는 사실로 쓴다.
- 보고서에 과정·라운드 수·점수를 넣는다. 최종 상태만 쓴다.

## 10. 파괴적 명령 가드
**언제**
- 삭제·덮어쓰기·포맷·강제 정리 같은 되돌릴 수 없는 명령을 실행하거나 건넬 때.
**절차**
1. 실행 직전에 대상을 다시 조회한다. 앞서 조회한 식별자를 재사용하지 않는다.
2. 명령 안에 신원 확인 조건을 넣는다.
   - 예: `[ 이름 = 기대값 ] && [ 크기 = 기대값 ] && 명령`
3. 대상의 이름, 크기, 사용량을 표로 보여 주고 승인을 받는다.
4. 가능하면 같은 이름의 다른 대상을 먼저 분리한다.
5. 되돌릴 수 있는 대안(이동, 보관, 미리보기 옵션)이 있으면 그것을 먼저 쓴다.
**종료 조건**
- 가드가 통과한 대상만 변경되었고, 사후 상태를 다시 조회해 확인했다.
**흔한 함정**
- 번호나 순서 같은 임시 식별자는 재연결·재정렬 때 바뀐다.
- 작업 공간의 추적되지 않는 파일을 일괄 삭제하는 명령은 쓰지 않는다. 다른 작업의 산출물이 지워진다.

## 11. 루프는 확인 주기를 두고 돈다
**언제**
- "될 때까지", "계속" 같은 반복 지시를 받았을 때.
**절차**
1. 시작할 때 두 줄을 말한다. 무엇이 완성인가(개수·분량·기간 예산), 언제 멈추고 보여 줄 것인가.
2. 3~5라운드마다 멈추고 결과를 보고한다.
   - 라운드별 신규 지적 수, 채택과 기각, 남은 위험.
3. 종료 조건에 도달할 수 없어 보이면 조건을 다시 협의한다.
4. 예산이 차면 그 상태로 보여 준다.
**종료 조건**
- 합의한 종료 조건에 도달했거나, 협의를 거쳐 조건을 바꿨다.
**흔한 함정**
- 산출물 분량이 늘어나는 것은 진행이 아니다.
- 무거운 검증(전체 테스트, 환경 기동)을 동시에 여러 개 돌리면 서로 느려진다. 하나씩 돌린다.

## 12. 요청받은 문서는 결론 먼저
**언제**
- 사람이 읽을 보고서·설명·변경 설명을 쓸 때.
**절차**
1. 첫 줄에 결론이나 권고를 쓴다. 선택지 나열보다 권고를 낸다.
2. 근거는 짧게, 불릿으로 쓴다. 한 줄은 80자 안팎이다.
3. 변경 설명은 한 문장 → 세 문장 → 코드 전/후 순서로 쓴다.
   - 사실이 아닌 문장은 diff와 대조해 걸러 낸다. 이 대조는 내 인과를 검증할 별도 독자에게 맡긴다.
4. 실제 이름(레포에서 검색되는 식별자)을 쓴다. 비유와 풀어 쓴 별칭을 쓰지 않는다.
5. 변명을 쓰지 않는다. 고칠 수 있으면 고치고, 남기는 것은 사실 한 줄이다.
6. 리뷰 과정(라운드, 점수, 도구)은 쓰지 않는다. 최종 상태만 쓴다.
**종료 조건**
- 처음 읽는 사람이 이 글만으로 무엇이 왜 바뀌는지 이해하고 검토를 시작할 수 있다.
**흔한 함정**
- 내 로컬 환경이나 작업 과정을 알아야만 이해되는 문장이 섞인다.
- 근거 없는 단정("영향 없음", "안전함")을 쓴다. 확인하거나 지운다.
- 길이를 채우려고 절을 늘린다. 변경이 작으면 설명도 작다.
