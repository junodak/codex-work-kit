# 짧은 시간에 작은 웹서비스를 만들 때

결론: 제공된 런타임으로, 서버와 화면을 한 프로세스에 두고, 업무 조건을 API에서 먼저 맞춘 뒤 화면을 얹는다. 화면은 사람이 직접 확인한다.

## 스택 고르기

- 과제나 기존 코드에 스택이 있으면 그것을 따른다. 바꾸지 않는다.
- 새로 만들면 제공된 런타임(`node -v`, `python3 -V`)에서 가장 단순한 것을 고른다.
  - 서버 하나가 API와 정적 화면(HTML·JS)을 함께 내보낸다.
  - 프레임워크·빌드 도구는 꼭 필요할 때만. 설치·빌드 시간과 실패 지점이 늘어난다.
- 고른 이유를 DECISIONS.md에 한 줄 남긴다.

## 순서

1. 업무 조건을 **계산·판정 함수**로 먼저 만들고 단위 테스트로 고정한다. 화면보다 먼저.
2. 그 함수를 감싸는 API를 만든다. 응답 형식을 정하고 바꾸지 않는다.
3. 화면은 API를 부르기만 한다. 업무 로직을 화면에 두지 않는다.
4. 핵심 사용자 흐름 하나를 끝까지 동작시킨 뒤 넓힌다.

## 구조 관례

- 데이터 읽기, 업무 로직, API, 화면을 파일로 나눈다.
- 포트와 경로는 환경변수로 받고 기본값을 둔다. 시작할 때 실제 주소를 출력한다.
- 원격 미리보기에서 열리도록 필요하면 `0.0.0.0`에 바인딩한다.
- 주어진 데이터 파일은 고치지 않는다. 가공 결과는 따로 만든다.

## 화면에서 사람이 직접 확인할 것

- [ ] 첫 화면이 뜨고, 핵심 흐름이 버튼·입력으로 끝까지 된다
- [ ] 결과가 없을 때 빈 상태 문구가 보인다
- [ ] 잘못된 입력이나 서버 오류에 메시지가 보인다 (흰 화면이 아니다)
- [ ] 시각·날짜가 업무 시간대로 보인다
- [ ] 숫자에 단위가 붙어 있다
- [ ] 개인정보가 화면에 그대로 나오지 않는다
- [ ] 새로고침해도 상태가 맞다

## 흔한 함정

- `localhost`에만 바인딩해서 미리보기에서 안 열린다.
- 정적 파일 경로가 실행 위치에 따라 달라진다. 파일 기준 경로를 쓴다.
- 서버를 고친 뒤 재시작하지 않아 옛 코드를 보고 있다.
- 서버를 띄운 터미널을 닫아 서버가 죽는다. 서버용 터미널을 따로 둔다.
- 화면에서만 검증하고 API·로직 테스트가 없다. 서술형에서 근거를 대기 어렵다.
- 시간대가 없는 날짜 문자열을 서버 시간대로 해석한다.

## 검증 명령

- `bash kit/scripts/check.sh`: 테스트 + 변경 상태
- `SMOKE_CMD="npm start" SMOKE_URL=http://127.0.0.1:3000/ bash kit/scripts/check.sh`: 서버를 띄워 응답만 확인하고 내린다
